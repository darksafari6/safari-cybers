## Roles and boundaries: start with the job

An order dashboard displays order totals. A separate workflow approves refunds. Both currently use the same database identity. The team argues that the dashboard never writes data, so the shared identity does no harm. What matters is what the database would permit, not just what the dashboard intends to do.

### Translate duties into permissions

Start with an access matrix. The reporting service needs to read the specific data used in totals. It does not need to issue refunds, read unrelated customer fields, or change permissions. The refund service needs a distinct identity and a record of changes it makes. A read-only view can be a useful boundary when it contains only the fields a caller needs and the caller cannot reach underlying tables directly.

```text
Reporting service  → read approved summary fields
Refund workflow    → update refund state through its approved interface
Migration identity → change schema only during authorized releases
```

### Worked review

If the reporting identity attempts to modify an order, the database should reject it even if an application bug asks for that action. Verify both that the expected report still works and that an out-of-scope operation is denied. Document who owns the permissions and when they should be reviewed.

### Checkpoint

A new report needs customer addresses for a legitimate operational purpose. Should every report gain access to addresses? Not necessarily. Give the specific workflow an explicit purpose and scope; consider aggregation or redaction before exposing a new field.

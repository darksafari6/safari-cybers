## The gateway that answered for the application

A fictional support portal is built from a browser, a gateway, and an application. The browser receives a response in 180 milliseconds, but the page says requests are temporarily unavailable. The application team insists its newest deployment passed all unit tests. Both statements can be true.

### Identify who actually responded

```text
Browser → gateway → application → database
          ↳ may respond without reaching the application
```

A gateway can reject a request, serve cached material, report that no backend is available, or wait for a backend and give up. A response therefore does not prove the furthest component in the chain handled it. In a well-instrumented system, request identifiers and timestamps help connect records across components. A missing record is not conclusive if sampling, retention, or clock differences could explain it.

### Worked example

The gateway records request `example-42` as a timeout after two seconds. A backend record for the same request says processing finished in 2.4 seconds. Together, these records suggest the gateway stopped waiting before the backend finished. They do not show why the backend was slow, or whether a retry performed the same work twice.

First ask whether the operation can safely be repeated. Repeating a page view and repeating a payment are different decisions. Then compare latency for similar operations, check the time window, and ask whether the slowdown began after a change or tracks unusual load. Increasing a timeout may reduce one symptom while leaving an overloaded service under pressure for longer.

### Checkpoint

Two teams use different dashboards: one reports gateway failures, the other application success. What makes both measurements accurate? They observe different boundaries. The application may record success after the caller has already received a failure. Select metrics that reflect the user-visible outcome as well as internal work.

## Query structure: values should remain values

A search feature accepts a customer-supplied name and a sort choice. These look like two ordinary inputs, but to a query builder they play different roles: the name is a value, while a sort column is part of the query structure.

### Draw the boundary

Bind the search term as data using the database driver's parameter mechanism. Keep the query structure fixed. For sorting, map a short set of product choices such as “newest” and “name” to known sort definitions, rather than using a raw column name provided by the caller. Treat authorization as a separate question: a structurally safe query can still return rows a user has no right to see.

### Worked example

A customer searches for `O’Connor`. A good regression test proves that punctuation behaves like ordinary text and that matching records belong to the caller’s authorized scope. Another test should reject unsupported sort choices or use the documented default. Neither test requires targeting another system.

### Checkpoint

The query is parameterized, but two teams share a reporting role. One team can view the other's orders. What failed? The access policy, not necessarily the query structure. Check both the row-level scope and the service identity before assuming one feature protects every boundary.

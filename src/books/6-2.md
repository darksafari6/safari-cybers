## Reversibility: design the exit before you deploy

A service owner proposes releasing a new dashboard at noon. The code can be rolled back quickly, but the release also transforms stored preferences. The team says “we can always revert.” Before accepting that claim, ask what can actually be restored and by whom.

### A rollback is a procedure, not a commit

Record the known-good release, who has authority to stop the rollout, and a measurable trigger. For example, if the rate of failed dashboard loads rises above the agreed threshold after the first group is updated, the release owner stops expansion and compares it with the unchanged group. Pick a baseline and a time window before you see the outcome.

The application and its data can have different recovery paths. If old code cannot understand newly written records, restoring only the application may leave users worse off. Prefer changes that leave both application versions able to read what they need during the transition. Document any irreversible step and the separate restore procedure it requires.

### Worked release card

- **Owner:** the on-call release engineer.
- **Watch:** failed dashboard loads and a test of saving a preference.
- **Trigger:** a sustained departure from the agreed baseline on updated instances.
- **Action:** stop rollout; restore the prior release if it is compatible with current data.
- **Verify:** test the original user workflow and watch for recurrence over the agreed window.

### Checkpoint

The error graph looks normal after rollback, but users can no longer load preferences created during the rollout. Was recovery verified? No. The aggregate graph missed a specific workflow, which is why technical metrics and user-visible checks belong together.

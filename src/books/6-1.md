## Review boundaries: the change hiding in plain sight

An engineer opens a pull request called “Clarify support documentation.” Most of the changes are prose. One file also changes the group allowed to see a customer export. The build passes. You are the last reviewer before release.

### Review the promise, not just the lines

Write down the expected effect of the change in one sentence. Then classify the files in the diff: documentation, behavior, permissions, data, or release configuration. A permission change may be completely legitimate, but its evidence belongs in the open. Ask what resource is affected, which people or services gain access, and why the existing role does not suffice.

A small change is easier to understand and easier to revert. Split unrelated changes where that separation makes their intent clearer. Don’t split a change merely to hide the relationship between two dependent files; a good review needs to see both halves of any invariant.

### Worked review

> The documentation changes are clear. The export role change is not described and expands who can access customer records. Please move it into a separate review with the intended audience, data scope, owner, and tests for both allowed and denied access.

Notice that the request names a concrete next action. “Looks risky” gives the author no way to resolve the concern. A signed-off access policy should also explain what happens when someone changes teams or no longer needs the capability.

### Checkpoint

A test proves a support lead can export records. Which second test would you request? Verify that a normal support user cannot export, including when they try to open the same application action directly. The user interface alone is not the boundary.

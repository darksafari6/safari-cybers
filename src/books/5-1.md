## Names, addresses, and applications

At 8:45 on Monday, Lina opens her team’s status portal. The address bar still shows the right name, but the dashboard never loads. A colleague in another office sees the page immediately. Both say “the internet works.” If you were asked to explain what failed, where would you start?

A useful answer begins by refusing to treat a web request as a single event. A browser needs to know where to connect, set up a connection, and receive a response that can be interpreted. Each step produces different evidence. By the end of this chapter, you should be able to sketch this sequence and explain what one successful step does and does not establish.

### Draw the request as a sequence

```text
Name typed in browser
    ↓ DNS: find an address for the name
Connection to the destination
    ↓ TLS: establish a protected session and check identity
HTTP request
    ↓ application or intermediary handles it
HTTP response
```

This is a useful model, not a promise that each visit starts from scratch. A browser may reuse a connection or a DNS result. Some HTTP versions use a different transport. An intermediary may answer without talking to the origin application. Start with the model, then update it as you learn how the actual system is deployed.

### Worked example: three different failures

**Case A: the resolver reports that the name does not exist.** The client did not get the address it expected from that lookup. Before blaming the application, check which name and resolver were used. The name might intentionally exist only inside the organization, or the client may be on a network that uses a different resolver.

**Case B: the client reaches an endpoint but rejects its certificate.** That tells us more than a timeout: a peer answered far enough for the client to inspect the certificate. It does not tell us that the peer was the intended application. Compare the exact hostname and the certificate’s validity information. Do not treat turning off verification as a fix; the goal is to restore the intended trust relationship.

**Case C: the browser displays an HTTP 503.** An HTTP component was reachable and returned a response. It may be the application, a gateway, or another intermediary. A 503 alone does not say whether the underlying cause was a database dependency, capacity limit, maintenance, or stale routing. The immediate question is which component generated it.

### A common wrong turn

A colleague says, “It can’t be the network—I can open a news site.” That is useful evidence about broad connectivity, but it is not evidence that the colleague can reach the portal. The destination, resolver behavior, and route can differ. A stronger comparison is the same portal from two clients at roughly the same time, recording what differs between those clients.

### Checkpoint: explain it aloud

> The dashboard loads the sign-in page, but clicking **Sign in** returns an error. Which facts can you state without guessing?

You know that some component served the page. You do not yet know whether the sign-in request reached the same host, whether it reached the authentication backend, or whether the user’s account is at fault. Find the failing request and record its time and response before assigning blame.

### Take it into practice

Draw two request flows: one that succeeds and one that stops before the application responds. Label the point of failure and write one observation you could share with a colleague. Replace broad statements like “server down” with precise statements like “client A received an HTTP response from the gateway at 08:45; the origin was not confirmed.”

### A second worked example: one name, two destinations

Imagine that `portal.example` is used from both a corporate network and outside it. Inside, the name resolves to the internal gateway. Outside, it resolves to a different gateway that shows an external sign-in page. This can be by design. If a learner reports two different answers, the first question is not “Which answer is wrong?” but “Which answer should this client receive in this context?” Compare against the documented routing and access model.

Suppose two office clients get different answers even though both should use the internal gateway. One was connected all morning; the other just joined the network. The connected client may hold an older cached result. A text log comparing the two without their connection history makes them look interchangeable when they are not. Capture the network context, time, answer, and whether the source was a fresh lookup or a cached result. An apparent routing puzzle can become a simple mismatch in client context.

Now change one fact: both clients reach the same gateway, and both load the sign-in page, but only one can access the dashboard afterward. The problem has moved beyond the initial lookup, but that does not prove it is an account issue. A different hostname might be used after sign-in. A client might never make that next request. The response might be an intentional denial rather than an outage. Follow the workflow one request at a time, and describe what you can see rather than what you expect.

### Compare good and bad notes

**Hard to act on:** “Internal portal broken since this morning. It looks like DNS or an account problem.” The statement gives no affected workflow, time window, or evidence. A colleague has to repeat the investigation from scratch.

**Helpful:** “At 08:45 UTC two clients in office A reached the internal sign-in page. One client received an HTTP error after submitting the form; the other opened the dashboard. We have not confirmed whether the failing request went to the same hostname. Next action: compare the failing request with the successful one and verify the responding component.”

Notice that the second note doesn't claim the incident is solved. It makes progress by narrowing the investigation and preserving a useful comparison. Precision matters more than certainty in the first few minutes.

### An independent practice prompt

A fictional help desk sends three reports:

1. A browser cannot look up the portal name while connected to a guest network.
2. A second browser reaches the portal but stops at a certificate warning.
3. A third browser loads the dashboard shell, but a request for recent activity returns a temporary service error.

For each, write the *furthest confirmed step*, the *first unresolved question*, and *one comparison you can make without changing configuration*. Then ask yourself whether your recommendation would accidentally weaken a security check or hide evidence from the person who investigates next.

<!-- model-answer -->

**Model approach:** In report one, compare the name and resolver against the intended guest-network policy. In report two, compare the requested hostname, presented certificate, and trusted context without dismissing the warning. In report three, inspect which component returned the error and compare a successful request for the same activity data. What looks like one incident in the help-desk queue may be three independent observations.
